# BareaPlay 리모델링 기준과 진행 상태

기준일: 2026-09-24. 시작 HEAD: e7cfe2e, master, clean.
사용자 요청은 전면적인 운영 흐름 개선이며, 운영 데이터 변경·배포의 포괄 승인이 아니다.

## 보존 계약

- 선수, 실제 출석/회비, 참석 응답/시각, 경기 기록, 기존 팀/라인업, 공개 스냅샷, 진행 중 비공개 설문을 자동 변경·삭제·이관하지 않는다.
- 기존 자동 팀 배정과 수동 편집은 유지한다. 8주 모드는 별도로 선택한다.
- 6쿼터 전체 편집이 기본이다. 9/10/11인제, 양 팀 공동 심판, 팀별 GK/휴식 순번과 전담 GK 예외를 보존한다.
- 고정팀 소속과 당일 차출은 다르다. 오늘 차출로 8주 원소속이나 설문이 변경되지 않는다.
- 조회, 미리보기, 이미지 생성은 Firebase 쓰기를 하지 않는다.
- 운영 데이터 쓰기 테스트를 하지 않는다. 배포 및 Rules 적용은 별도 승인한다.

## 새 고정팀 저장 계약 — 구조 승인, 운영 적용 전

2026-09-24 사용자가 별도 teamCycles 구조와 이후 권한 적용·배포를 승인했다. 통합안 에뮬레이터 검사는 통과했으나 콘솔 게시/규칙 조회 오류로 활성 적용을 확인하지 못했다. 저장 기능은 계속 잠근다.

`teamCycles/{autoId}`: schemaVersion:1, startDate, endDateExclusive(시작+56일),
members:[{name,team:0|1,role,second}], createdBy, createdAt.

- 관리자만 읽고 새 계획을 생성한다. 기존 주기는 수정/삭제하지 않고 새 주기로 보존한다.
- 조회된 설문은 감독이 미리보기에서 확인할 때만 사용한다. note, Google 계정 정보, 설문 원본, 선수 능력치를 복제하지 않는다.
- name은 기존 선수 키를 참조한다. ID 마이그레이션은 이 단계 범위가 아니다.
- 1·2지망이 같으면 한 역할 집중으로 표시한다. 미응답/중복계정 답은 추정하지 않고 감독 확인 대상으로 표시한다.
- 초안은 인원·역할별 수·능력치·직전 주기 같은 역할의 조합을 고려한다. 가능한 유일한 정답이나 선호 보장을 뜻하지 않는다.
- 당일 미리보기는 참석자만 추려 인원 부족 팀에 최소 차출을 제안한다. 부족한 역할/보내는 팀의 역할 여유를 우선하고, 원소속은 보존한다. 새 참석자는 임시 팀/역할을 감독이 지정한다.
- 미리보기는 기존 '직접 팀 입력'에만 전달한다. 실제 날짜별 배정 적용은 기존 확인 동작을 거친다. 기존 라인업을 자동 생성/삭제하지 않는다.
- 활성화 전 Rules에서 포괄 공개 읽기/일반 쓰기 허용의 teamCycles 예외도 반드시 추가한다. 새 match 블록만 추가하면 공개 규칙을 이기지 못한다.
- 복구: 기능 플래그를 닫고 기존 자동/수동 배정 사용. 새 문서는 보존하며 이전 주기/기존 경기 자료는 그대로 사용한다. 기존 데이터 이관은 없다.

## 단계별 인수 기준

1. 안정화: 한도/연결 실패 구분, 선택 보존, 중복 읽기 감소, 오프라인 가짜 데이터 회귀 검사 기준 정비.
2. 작업 공간 정리: 중복 내비게이션 제거, 6쿼터 전체 편집, 공개 확정본의 팀별 PNG 저장/공유. 데이터 편집과 공유 분리.
3. 8주 계획: 최근 3개월 실제 출석 기반 명단, 설문 누락/중복 검토, 고정팀 초안/수동 수정, 주기 저장, 당일 차출 미리보기. 관리자 권한 검증 후 활성화.
4. 후속 구조 개선: 통일된 경기 선택, 저장 중/실패/공개본 차이 표시, 동시 수정 방지, 필요한 화면만 기록 조회, 공개 화면 독립 로딩. 별도 단위로 구현·검증한다.
5. 운영 전환: 변경 목록/검증 결과/미검증을 보고 → Firebase 권한·commit/push·배포 승인 → 실제 제출은 사용자 본인의 정상 투표로 확인.

단계 3의 저장 준비가 전체 리모델링 완료를 의미하지 않는다. 이후 감독 계정 인계, 과거 확정본 정정 이력, 백업 체계도 별도 인수 대상이다.

## 후속 작업 결과 (배포 후보)

- 8주 훈련 역할 연결: 사용자가 명시적으로 적용한 계획과 날짜에서만 작동한다. 기존 생성기가 GK/휴식/심판과 출전자를 정한 후 필드 자리만 최적 배치한다. 수동 필드 고정 우선. 1지망 수용 인원 초과 시 쿼터별 훈련 기회 편중을 줄이고, 2지망은 차선으로 사용한다. 과거 라인업을 로드하거나 계획을 선택하는 것만으로 재배정하지 않는다.
- 경기 저장 안전장치: 지연된 입력을 다른 날짜에 저장하지 않도록 입력 상태를 즉시 잡고 저장만 지연한다. 날짜 변경 전에 이전 저장을 기다린다. 실패하면 날짜와 편집을 유지하며 트랜잭션 충돌 시 타 기기를 덮지 않는다. 명시적 확인 후 서버본을 다시 불러올 수 있다.
- 공개: 현재 화면의 저장과 공개를 구분하고, 이번 화면에서 공개한 이후의 변경 여부를 표시한다. 확인하는 동안 팀·라인업·선택 경기가 바뀌면 공개하지 않는다. 서버 공개본 전체 이력 비교/수정은 아직 제공하지 않는다.
- 운영 UI: 메뉴를 참석 → 팀 → 6쿼터 → 출석·회계 → 기록 → 선수 → 가이드 순으로 정리했다. 별도 중복 단계 버튼은 없다. 감독 보드와 반복 수정에 따른 성향 제안은 접힌 고급 도구로 남겼으며 제안 기록을 자동 조회하지 않는다.
- 로딩: 공개 화면의 관리자 모듈 분리, 대형 차트·엑셀 도구 지연 로드, 외부 폰트 제거, 초기 장부 중복 조회 제거. 선수 데이터가 준비되지 않았으면 새 자동 배정을 막고, 회계 자료가 불완전하면 회계 편집을 막는다. 연결 지연 안내는 앱/Firebase 모듈과 독립적이다.
- 업데이트: SW 기본 다운로드에서 관리자 전용 묶음을 제외하고 사용 시 캐시한다. 즉시 교체를 중단했다. 기존 버전의 관리자는 저장 후 새로고침해야 하며 새 버전/구버전 혼용 중 동시 수정은 피한다.

## 검사 범위와 남은 인수 항목

- `npm test`: 순수 로직 55개. 추가된 검사는 훈련 포지션/DM·AM/고정 자리/의무 보존/경쟁 역할 분배, 날짜별 저장 큐, 실패·재시도·동시 수정 보존, SW 설치 대기·캐시 경계다.
- `tests/browser-smoke.cjs`: 기본 흐름 및 `--operations`, `--ratings`, `--survey`, `--remodel`, `--saves`, `--loading` 경로를 검사한다. 별도 Playwright/Edge 실행 환경이 필요하다. 모든 Firebase와 외부 요청은 가짜 자료로 대체하거나 차단한다. `--remodel`에서만 테스트 프로세스 내부의 고정팀 저장 플래그를 켠다.
- 기존 회비·출석·투표·설문 보존, 관리자 초기 로딩 0쓰기, 미지의 경기 필드 보존, 한도 오류에서 투표 선택 유지, 장부 일부 조회 실패, 손상된 로컬 캐시, 공개 화면의 관리자 코드 장애 독립성을 확인했다.
- 실제 Firestore Rules를 콘솔에서 대조했다. 기존 admins/ratings/ratingResults/ratingParticipation/privatePositionPreferences 예외를 그대로 두고 teamCycles만 추가한 통합안을 별도 공식 에뮬레이터에서 499건 검사했다. 실제 코치 UID는 가짜 값으로 바꾼 뒤 기존 원문과 정규화 비교했다. 승인 후 콘솔 게시를 시도했으나 오류가 발생했고 새 탭의 규칙 목록 조회도 실패했다. 게시 성공 확인 전 저장 기능은 켜지 않는다. 운영 테스트 문서는 만들지 않았다.
- 실제 Chrome/Safari/카카오 인앱, PNG OS 공유 선택창, 기존 설치 PWA의 새 버전 적용은 운영 전환 시 사용자 실기기 확인이 필요하다.
- 관리자 화면은 여전히 전체 장부를 한 번 구독한다. 생성 시 전체 과거 배정 조회도 남아 있다. 날짜별 페이지 나누기는 별도 개선 단위이며 이 단계에서 회계 집계를 부분자료로 바꾸지 않았다.
- 공통 스타일은 아직 Tailwind CDN을 사용한다. 그 요청 자체가 지연되면 복구 안내가 나오지만 CDN 장애를 완전히 없앤 것은 아니다. 테스트의 CSS 대체본으로 실제 모든 기기의 시각적 품질을 보증할 수 없다.
- 활약투표의 실제 저장 성공·할당량/과금 상태·백업은 로컬 검사로 입증할 수 없다. 한도 오류 안내와 불필요 조회 감소가 요금제/사용량 제한 자체를 해결한 것은 아니다.
- commit/push/Vercel 배포 승인을 받았다. 이 문서는 배포 후보의 검사 기록이며 실제 배포 상태는 연결된 Vercel 배포에서 확인한다. 권한 적용 미확인 때문에 고정팀 저장만 비활성 상태로 배포한다.

## 실제 Rules 격리 검사 재현

- `tests/firestore-rules.cjs`는 `127.0.0.1:8087`의 `demo-bareaplay-rules` 가짜 프로젝트만 사용한다. 호스트가 다르면 중단한다. 운영 설정·키·로그인이 필요 없다.
- `tests/fixtures/firestore-before-cycles.rules`는 기존 규칙의 검사 전용 사본이며 감독 UID가 `test-coach`로 대체되어 있다. 이 사본은 배포하면 안 된다. 통합 대상은 콘솔의 실제 기존 규칙이다.
- 검사 스크립트는 `docs/TEAM_CYCLE_RULES_DRAFT.txt`의 match 조각과 두 포괄 예외를 적용해 전후를 비교한다. `node tests/firestore-rules.cjs`로 실행하며 별도 `@firebase/rules-unit-testing`, `firebase` 모듈 및 Firestore 에뮬레이터가 필요하다.
- 이번에는 시스템 전역 설치 없이 임시 폴더의 Firebase 공식 npm 도구, 공식 Java 21 휴대용 실행 파일(다운로드 체크섬 확인), Firestore 에뮬레이터 1.22.0을 사용했다. 실제 프로젝트 의존성이나 계정 자격정보는 바꾸지 않았다.
