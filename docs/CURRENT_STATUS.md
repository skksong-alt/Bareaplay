## 7. 확인된 Firebase 데이터 손상 위험

1. 선수 엑셀 업로드는 `players`의 모든 문서를 삭제한 다음 새 자료를 다시 생성한다. 빈 파일, 잘못된 입력 또는 중간 실패 시 전체 또는 일부 선수 데이터가 사라질 수 있으며 트랜잭션과 자동 롤백이 없다.
2. 출석 저장은 선택 날짜에서 체크 해제된 선수의 기존 `attendance` 문서를 삭제하고 중복 문서도 정리한다. 불완전한 명단을 저장하면 기존 회비 정보가 함께 삭제될 수 있다.
3. 현재 보기 범위의 `attendance` 기록 전체 삭제 기능과 개별 회비 기록 삭제 기능이 있다.
4. 선수 이름 변경은 새 이름 문서를 생성하고 이전 이름 문서를 삭제하지만 과거 출석, 투표, 팀, 평점, 비고의 이름 참조를 함께 변경하지 않는다.
5. `dailyMeetings/{date}` 저장은 `merge` 없는 전체 덮어쓰기다. 여러 관리자의 동시 편집 또는 오래된 화면의 저장으로 마지막 저장이 앞선 내용을 덮을 수 있다.
6. 경기 능력치 보정과 완료 플래그 저장이 하나의 트랜잭션이 아니다. 부분 실패 또는 사용자의 중복 승인으로 선수별 점수가 불일치할 수 있다.
7. 지난 투표와 응답, 선수, 지출, 기타 수입, 장소는 영구 삭제 경로를 가진다.
8. `playerNotes/all`은 선수별 비고 전체 맵을 한 번에 덮어쓰므로 동시 수정 시 마지막 저장이 다른 변경을 덮을 수 있다.
9. 코드의 관리자 UI 검사만으로 서버 보안을 보장할 수 없다. 실제 데이터 보호는 배포된 Firestore Security Rules에 의존한다.

5. Firebase 쓰기 코드를 테스트 가능한 경계로 분리하고 Emulator 기반 통합 테스트를 추가한다.
6. 명시적 승인 후 선수 엑셀 전체 삭제·재생성 경로부터 미리보기, 검증, 백업 및 복구 가능한 방식으로 개선한다.
7. 출석 범위 삭제, 이름 변경, 능력치 보정의 원자성과 복구 절차를 개선한다.
8. 이후 기능을 한 단위씩 수정하고 구문 검사, 영향 점검, 승인 후 commit·push·배포한다.
9. 배포가 필요한 변경에서는 모듈 `?v=`와 Service Worker 캐시 버전을 함께 검토하고 기존 사용자 업데이트를 확인한다.
