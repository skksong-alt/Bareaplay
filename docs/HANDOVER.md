# BareaPlay 감독·기술 운영 인수인계

이 문서는 인계 절차이며 실제 권한·소유권 변경을 실행한 기록이 아니다. 운영 앱과 데이터는 그대로 유지한다. 인계 시점에 서비스 화면과 공식 문서를 다시 확인한다.

## 1. 새 감독이 먼저 익힐 것

참석·모임정보 → 팀 배정 → 라인업·공개 → 실제 출석·회비 → 경기기록 순서로 운영한다. 모든 화면에서 경기 날짜를 확인한다. 참석 투표와 실제 출석, 편집 저장과 팀원 공개는 각각 별도다.

- 참석: 제목만 바꾸지 말고 실제 날짜·시각·구장을 확인한다. 지난 경기 활약투표는 다음 참석 투표에서 연결한다.
- 팀: 일반 자동 배정, 직접 입력, 8주 고정팀 중 상황에 맞는 방법 하나를 사용한다. 초안만 보고 있으면 아직 적용된 것이 아니다.
- 라인업: 기본 6쿼터, 선택 4쿼터. 4쿼터에서 기존 5·6쿼터는 보관된다. 경기 인원은 별도로 9/10/11인제를 고른다.
- 수정: 이미 완성한 팀을 재생성하지 말고 필요한 선수만 이동한다. 저장 실패 시 새로고침하지 않는다.
- 공개: 양 팀 전체 배치·빈자리·심판·키퍼·휴식을 확인한 뒤 라인업 탭 맨 아래에서 확정한다. 이전 링크는 이전 공개본이다. 수정 후 다시 공개하고 최신 이미지도 재공유한다.
- 회계: 체크 저장은 신규 출석 추가만 한다. 체크 해제나 중복 발견으로 기존 기록을 자동 삭제하지 않는다. 일부 납부자는 미수금 확인 대상이다. 행별·범위 삭제는 별도 확인이 필요한 영구 삭제다.
- 평가: 경기 결과·동료 활약투표는 참고 자료다. 승패를 개인 능력치에 자동 반영하지 않는다. 8주 동안 같은 역할의 판단·기본기·협력을 관찰하고 본인 의견과 함께 감독이 평가한다.

## 2. 8주 운영 계획

1. 최근 3개월 참석자와 비공개 희망 포지션의 미응답·동명이인·중복 응답을 확인한다.
2. 같은 두 지망은 한 역할 집중 희망, 서로 다른 지망은 두 역할 학습 희망으로 이해한다. 강제 배정 약속은 아니다.
3. 포지션 수요와 감독의 기존 선수 평가를 함께 보고 고정 A/B팀을 만든다. 선수 능력치나 설문 원본은 변경하지 않는다.
4. 매주 실제 참석자만 추리고 부족한 팀에 필요한 포지션을 최소한으로 차출한다. 당일 차출은 원소속 변경이 아니다.
5. 라인업의 훈련 포지션 우선 여부를 확인한다. 심판·GK·휴식 순번과 수동 고정은 별도로 유지한다.
6. 4주차에 피로·희망·편중을 점검하고 8주차에 다음 계획을 검토한다. 매주 편의를 위해 전체를 다시 섞지 않는다.

`teamCycles`의 운영 권한 배포는 아직 확인되지 않아 저장 기능은 차단되어 있다. 차단을 해제하기 전에 실제 Rules 게시 성공을 확인해야 한다. 로컬 검증 통과만으로 활성화하지 않는다.

## 3. 권한은 다섯 곳을 따로 확인

| 대상 | 실제 역할 | 인계 시 확인 |
| --- | --- | --- |
| 앱 관리자 | 선수·회계·팀·라인업 운영 | 새 Google 계정의 앱 관리자 등록. 기존 관리자 검증 구조 유지 |
| 비공개 포지션 설문 | 감독만 전체 응답 조회 | 현재 Rules의 감독 식별 조건 별도 변경 승인. UID를 공개 문서에 기록하지 않음 |
| Firebase/Google Cloud | 프로젝트·Firestore·청구·서버 권한 관리 | 기존 프로젝트에 새 담당자 초대. 운영 권한과 결제 책임 별도 확인 |
| GitHub | 코드와 master 이력 | 저장소 접근, 보안 인증, Vercel 연동 권한 |
| Vercel | 운영 배포·도메인·환경변수 | 새 담당자 접근, 청구, Git 연결, 운영 환경, OIDC 신뢰 조건 |

비밀번호·인증키·토큰·환경변수 값을 이 문서, 카톡, Git에 기록하지 않는다. 접근 권한이 없는 경우 우회하지 않고 소유자에게 초대를 요청한다.

## 4. 안전한 실제 인계 순서

### 준비: 기존 담당자와 함께

- 현재 HEAD, master와 원격 일치 여부, 운영 배포 상태, 도메인과 외부 연결 목록을 확인한다.
- 백업 존재 여부·복구 절차를 읽기 전용으로 확인한다. 백업 생성은 비용·저장 위치·권한을 설명하고 별도 승인 후 실행한다. 아직 검증되지 않은 백업을 있다고 가정하지 않는다.
- 진행 중인 경기·투표·설문을 목록으로 확인한다. 인계 시간에는 양쪽에서 동시에 같은 경기를 수정하지 않는다.
- 계정 초대·Rules 수정·서비스 소유권 이전·청구 변경·배포는 각각 범위와 시점을 승인받는다.

### Firebase/Google Cloud

새 DB를 만들어 복사하지 말고 기존 프로젝트에 새 계정의 접근을 부여한다. 필요한 역할을 검토하고 새 계정의 실제 접근을 확인한다. 이전 담당자 제거는 마지막에 한다. 프로젝트 소유권과 Billing 권한은 별도 검토 대상이다. [Google Cloud 프로젝트 소유권 변경](https://support.google.com/cloud/answer/7283495?hl=en)

앱 `admins` 권한과 비공개 설문 감독 조건은 Cloud IAM과 별개다. 새 감독 로그인 후 허용된 화면만 열리는지 확인한다. 설문 전체 조회를 일반 팀원에게 열지 않는다. 운영 테스트 응답을 만들지 않는다. Rules 변경은 배포 전 에뮬레이터로 익명/일반 사용자/감독/관리자를 검증한다.

### GitHub

먼저 공동 접근으로 업무가 가능한지 확인한다. 소유권 변경이 꼭 필요하면 저장소 Transfer 절차를 별도 승인받는다. 이전 후 원격 주소·연결된 앱·배포 권한을 확인한다. master, 커밋 이력, 기존 자료를 유지한다. force push나 새 저장소로 이력 없는 복사 작업을 하지 않는다. [GitHub 저장소 이전](https://docs.github.com/en/repositories/creating-and-managing-repositories/transferring-a-repository)

### Vercel + Firebase 서버 연결

먼저 새 담당자에게 기존 팀/프로젝트 접근을 제공한다. 다른 Vercel 팀으로 실제 이전할 경우 Git 연결·도메인·운영 브랜치·환경변수 존재 여부·통합 기능·청구를 확인한다. 모든 통합이 자동 이전되는 것은 아니다. 값 자체를 화면 캡처나 문서에 남기지 않는다. [Vercel 프로젝트 이전](https://vercel.com/docs/projects/transferring-projects)

활약투표 서버는 키 없는 OIDC 연결을 사용한다. Vercel 팀/프로젝트/환경과 관련된 토큰 조건이 달라지면 Google Cloud의 신뢰 조건과 서비스 계정 연결도 재검토해야 한다. 일반 방문자가 Firebase를 직접 쓰게 열어 우회하지 않는다. 기존 연결을 먼저 제거하지 말고 새로운 연결을 승인·검증한 뒤 정리한다. [Vercel OIDC 참조](https://vercel.com/docs/oidc/reference)

### 완료 판단

- 새 감독 계정으로 운영 메뉴 및 비공개 설문 조회가 허용 범위 안에서 된다.
- 기존 참가자·회비·출석·경기·투표 응답 수와 최신 날짜가 유지된다.
- 일반 팀원의 참석/설문/공개 라인업 조회와 서버의 공개 집계 읽기를 확인한다. 원본 활약 선택은 공개하지 않는다.
- GitHub와 Vercel의 승인된 배포 경로를 확인한다. 운영 데이터 쓰기 테스트는 하지 않는다.
- 양쪽 담당자가 확인한 뒤에만 불필요해진 이전 권한을 별도 승인으로 제거한다.

## 5. 장애와 복구

저장 실패 시 원본을 지우거나 새 프로젝트를 만들지 않는다. 회계의 실패한 변경은 브라우저 메모리에서 재시도할 수 있으나 창을 닫으면 사라진다. 경기 저장 충돌은 다른 기기를 자동 덮어쓰지 않으므로 양쪽 내용을 비교해야 한다.

코드 문제라면 검증된 이전 동작을 새 수정 커밋으로 복원하거나, 승인된 이전 배포로 전환하는 계획을 보고한다. git reset/revert/clean/force push는 실행하지 않는다. 코드 복구는 DB 복구가 아니다. 데이터 복구는 백업/시점복구의 실제 가용성·비용·덮어쓰기 영향을 확인하고 별도 승인받는다.

활약투표 한도·권한 오류와 teamCycles Rules 게시 실패는 운영 검증 미완료 항목이다. 실패 메시지를 숨기거나 성공으로 표시하지 말고 실제 해결과 로컬 코드 완료를 구분한다.
